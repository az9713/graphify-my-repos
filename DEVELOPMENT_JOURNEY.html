Development Journey — Portfolio Atlas & Repo Graph

From "suggest me some ambitious projects" to a clustered atlas of 448 repositories and an Obsidian-style physics graph. Two sessions, four deliverables, several wrong turns worth recording. no git repo files on disk are the record

The opening ask

"i have 25% weekly usage left. it will be reset tomorrow 8pm. please scan my GitHub repos. suggests some ambitious projects that

1. extend and/or fix existing ones
2. create new projects in domains that i have not attempted before.

consider this is the chance for you to show off your vast knowledge, imagination and creativity. There are no limits on the topics except the stated usage. please suggestions only. no implementation yet."

Two constraints shaped everything that followed. A hard token budget with a deadline — which made every expensive step a decision rather than a reflex. And "suggestions only" — the deliverable was judgement about a body of work, not code. To have judgement worth anything, the work had to be read first.

The four follow-up prompts across both sessions, in order: "please output a html for these suggestions" → "run A1 now — graphify all 448 repos" → "Do we have a graph" → (new session, after a handoff) "create the graph… I have a recent project that also created an Obsidian-like graph based on physics. look it up how it was done and use the same skill here." Everything below hangs off those five sentences.

Chapter 1

Reading 448 repositories

The first move was mechanical: pull every repository on the account through the GitHub API, then pull each README. That produced the corpus that every later step reads from:

ArtifactWhat it is
corpus/repos_raw.jsonUnfiltered API response for all 448 repositories (~2.4 MB)
corpus/repos.jsonTrimmed metadata: name, description, language, stars, forks, created/updated, topics, fork flag, size
corpus/docs/*.md448 markdown files, one per repository: YAML front matter plus README truncated to 20k characters

One repository's README came back empty and stayed empty — noted rather than patched, because a missing README is itself a fact about the portfolio.

Problem: the API output crashed the reader

Symptom: reading the GitHub API output in Python died on certain repository descriptions.

Cause and fix: Windows defaults to a legacy code page; repository descriptions contain emoji and non-Latin characters. Every read of API output is pinned to encoding='utf-8'. Small, but it recurred often enough to be worth writing down.

Chapter 2

The suggestions page

With 448 READMEs read, the first deliverable was a single self-contained HTML page: 16 project suggestions across two tracks — Track A extends seven existing repositories, Track B opens nine domains the portfolio has never touched. Each idea carries a cost rating (in the same budget currency the user was worried about), a concrete first move, and an explicit "the hard part" section so no idea reads as free. Filter chips at the top; no external assets.

Design decision: cost as a first-class field. The opening prompt named a budget, so every suggestion states what it would spend. A suggestions page that ignores the stated constraint is a wish list, not advice.

That page later turned out to contain two claims the data disproved. That story is Chapter 5 — and it is the most useful thing in this document.

Chapter 3

"run A1 now — graphify all 448 repos"

Suggestion A1 was to build a knowledge graph over the whole portfolio and see what the account is actually about. The user green-lit it. This was the single most expensive step of the project:

Problem: 3.4M tokens bought a vendor graph, not a subject graph

Symptom: every one of the top 40 concepts by degree was a technology — the coding-agent CLI itself (264 edges), Python (126), TypeScript (86), then model names, protocols, frameworks. Clustering that graph groups repositories by which tools they use. In a portfolio that shares one stack, that collapses: 146 communities, median size 2, 50 singletons. Useless as a map.

Cause: LLM concept extraction surfaces named entities, and in technical writing the named entities are dependencies. Subject matter lives in the prose, not in the proper nouns.

Fix: split the job by what each method is actually good at. TF-IDF + SVD + KMeans locally for "what is this about" — seconds, zero tokens. The extracted graph kept for what it genuinely encodes: shared-tooling structure, and therefore hubs, bridges and orphans.

Chapter 4

Two clusterings, two failures, two fixes

Failure 1 — clustering on README furniture

The first TF-IDF pass produced fourteen clusters, four of which were junk: they grouped documents by installation instructions, badge markup and table-of-contents boilerplate. The vectorizer was reading the scaffolding, not the content — including the YAML front matter that the corpus builder had added itself.

The rewrite strips aggressively before vectorizing, in this order:

strip YAML front matter      # self-inflicted: added during corpus build
strip fenced code blocks
strip HTML / badge markup
strip markdown links and images, and bare URLs
strip file-path tokens       # docs/troubleshooting.md and friends
strip table and rule chrome
then: drop any term containing a word from a ~90-word boilerplate stop list
      (install, quickstart, prerequisites, npm, the tool and model names, …)

Then TF-IDF with bigrams (max_df=0.30, min_df=5, sublinear term frequency) → SVD to 120 dimensions → row-normalise → KMeans at k=14. The failed script was kept on disk, explicitly labelled as the broken version, because a record of how it failed is worth more than a clean directory.

Calibration note: silhouette ≈ 0.04 is not a verdict

Every k from 10 to 18 scored near 0.04. For text embeddings that is normal and is not evidence of "no structure" — clusters overlap by construction. The usable test is whether the top terms per cluster are interpretable by a human. They were, so k=14 was chosen and each cluster was hand-named from its terms and exemplars.

Failure 2 — the hairball

The second clustering runs on the extracted graph, projected repo-to-repo. Done naively, one universal concept creates a clique of hundreds of repositories and the whole graph fuses into a single blob. The projection rule that fixed it:

drop any concept appearing in more than 120 repositories   # universal → carries no signal
weight each shared concept by 1 / (k - 1)                  # Newman weighting; k = repos sharing it
prune edges with weight <= 0.02                            # cuts what survives into something modular

Louvain resolution was then swept from 0.3 to 1.5 and the first setting landing in the 8–16 communities range was taken — a deliberately boring selection rule, chosen in advance so the number of communities is not tuned to taste. Betweenness centrality was sampled (180 pivots) rather than computed exactly; exactness is not needed to rank bridges.

The merge

A third script joins the three sources into one record per repository — subject cluster and cluster name from the text clustering, tooling community, neighbour count and betweenness from the graph, stars/language/dates/topics/homepage from the API — and derives the summary statistics, the orphan list, the top 15 hubs and the top 15 bridges. Three clusters whose top terms are generic are flagged vague in the data itself rather than quietly presented as subjects.

"Derivative" is a heuristic, and worth stating plainly: a repository counts as derivative if the API marks it a fork, or if its name or description contains clone of, fork of, port of or tutorial. It will miss an unmarked reimplementation.

Chapter 5

The atlas — and the corrections that overturned the suggestions

atlas.html presents all 448 repositories: a reach chart, expandable cards for each of the 14 clusters listing every member, the orphan list, and a hub/bridge table. Data is injected into a template at build time through a /*__DATA__*/ placeholder — the template is the file to edit; the generated page is overwritten on every rebuild.

The point of building it was not the page. It was that the numbers contradicted the advice given one chapter earlier:

Claim in the suggestions pageWhat the data showed
Original work earns more attention than derivative work False. Derivative repositories average 0.68★, originals 0.54★ — indistinguishable noise. Stars track subject, not originality: six agent-tooling clusters hold 268 repositories and 244 stars; the six covering physics, trading, film, courses, knowledge graphs and deployed apps hold 113 repositories and 11 stars.
Discoverability was treated as a content problem Missed the cheapest fix. Only 15 of 448 repositories have GitHub topics set; only 37 have a homepage URL. That is a metadata fix, not a content fix, and it was absent from the original advice.
"Roughly 180 derivative repositories"120.
Trading cluster ≈ 13 repositories17 — which changes the scope of the suggestion built on it.
A CFD-specific suggestionThe physics and math cluster is 24 repositories and much broader than CFD; the suggestion should widen.
—147 repositories sit in two clusters whose top terms are generic. Roughly a third of the portfolio is agent infrastructure too self-similar to separate.

Design decision: publish the corrections, do not silently patch the earlier page. The suggestions page still carries its two disproven claims, with the atlas holding the corrections and the handoff note recording which is authoritative. Overwriting would have erased the more interesting artifact — the record that reading the data changed the conclusion.

Problem: three sections of the atlas rendered blank and the file looked perfect

Symptom: the page validated, the server returned 200, the source read correctly — and the cluster cards, orphan list and hub table were all empty.

Cause: one missing field on one object threw inside a template literal during rendering, which abandoned every DOM assignment after it. The browser console showed no page error at all — only an unrelated browser-extension exception.

Fix, now standing practice: screenshot every section of a JavaScript-rendered page before calling it done. Two mechanics that cost time: file:// URLs are refused by the browser tooling, so pages are served from a local HTTP server on a loopback address; and a screenshot taken immediately after a scroll sometimes returns a blank frame, so a section is never declared broken on a single capture.

Interlude: the handoff

This directory is deliberately not a git repository, so there are no commits to resume from. Before the context was cleared, a HANDOFF.md was written to carry the state: what exists, what was disproven, where to read each artifact, the exact run order of the scripts, the gotchas that had cost time, and one clearly-specified next task. The next session started from that file — and the graph chapter below is that task being executed.

Chapter 6

The graph

"create the graph. i have a recent project that also created an Obsidian-like graph based on physics. can you look it up how it was done and use the same skill here"

The second instruction mattered more than the first: it turned an open design task into a port. One content search across the projects directory for force-simulation vocabulary (forceSimulation, repulsion, force-directed, barnes-hut) returned 25 files, two of which were the earlier project — a brainstorm note and, next to it, a finished build: a Python slimming script, a vendored physics library, an HTML template, the generated viewer.

The inherited insight: "drag-lag" is not a feature, it is physics

The Obsidian behaviour people actually want — grab a node, its neighbours trail after it with a springy delay — is not implemented by anyone. It falls out of any live force simulation: links are springs, nodes repel, velocity is damped. Pin the dragged node to the cursor, keep the simulation running, and velocity decay is the lag. So the library question reduces to: whose drag handler keeps the simulation alive? The earlier note had already answered it — force-graph (Canvas 2D, d3-force inside) re-heats on drag by default. Not re-litigated here: sigma.js needs manual glue, vis-network will not scale, Cosmograph has the wrong interaction model, raw d3-force is what force-graph already is.

What was rebuilt rather than reused

  • The edge list did not exist. The clustering script emits community assignments and centrality but never wrote the edges, so the build script recomputes the projection from scratch using the identical rule (drop >120, weight 1/(k-1), prune ≤0.02) — 7,581 edges over the repositories that survive the join.
  • Top-6 ties per repository. The full projection lays out as one uniform ball: every node pulled in every direction averages to no direction. Capping each node at its six strongest edges (union, so nothing is orphaned by the cap) cuts it to 1,551 edges and lets structure appear.
  • Size by stars, not degree. Degree here is an artifact of the projection; stars are the outcome worth seeing. Radius is 3 + 1.7·√stars, with a thin white ring on anything above zero — with 363 of 448 repositories at zero stars, size alone would be invisible.
  • Fit frames the connected core only. Disconnected repositories drift into a wide halo; fitting the whole extent shrinks the interesting part to a smudge. The fit call takes a node filter, so it frames nodes with at least one neighbour and lets the orphans sit off-frame — which is also exactly the "orphans at the margin" the brief asked for, obtained by not fighting the physics.

Problem: the hairball that was not a hairball

Symptom: the first render was a perfectly even disc of dots — no clumping, no gaps, crisp circular boundary. It read as "this data has no structure".

Cause: it was not a layout. It was d3-force's initial phyllotaxis seeding pattern, which happens to be an even disc. The simulation had never run. Tell-tale: node 0 sat at exactly (7.07, 0), and screenshots stayed pixel-identical across completely different force settings.

Problem: why the simulation never ran

Symptom: zero ticks. Re-heating did nothing. Re-setting the graph data did nothing.

Cause: the automated browser tab reported document.visibilityState === "hidden" — the window was behind other windows. Chrome throttles requestAnimationFrame to zero in hidden tabs, and the library drives its physics from that loop. Screenshots still captured fine, which is what made the frozen image convincing rather than obviously broken.

Fix: verify through a channel whose page is genuinely visible. Standing guard for any animated page: log document.visibilityState and compare two node positions 1.5 s apart before believing a screenshot of anything that moves.

Problem: a hand-rolled gravity force collapsed the graph to a point

Symptom: after adding a four-line custom force to pull disconnected nodes back toward the centre, every node sat at exactly (0, 0).

Fix: delete it. The built-in centering force already does the job, and the orphans settle into a natural halo — connected repositories inside roughly 670 units, disconnected ones at a median radius of about 808. The requested behaviour came from removing code, not adding it.

Problem: tuning physics against a stopped simulation

Symptom: several rounds of force-parameter changes appeared to do nothing.

Cause: two compounding traps — the hidden-tab freeze above, and the fact that once a simulation has cooled, live parameter edits do not restart it. Every apparent "no effect" was really "no ticks".

Fix: tune in a visible page, re-seed positions and re-heat explicitly between experiments, then bake the winning numbers into the template. Final values: charge −120 with a 400-unit cutoff, link distance 25, link strength min(1, weight × 10), 20 s cooldown.

What the graph actually said

Once the physics ran, the honest answer to "do the subject clusters separate in space?" was no. Measured in the running page: only 15.7% of connected repositories sit closer to their own cluster's centroid than to any other — against 7.1% expected by chance across 14 clusters. Barely twice random.

That could mean the links carry no structure, or that they carry a different structure. One toggle distinguishes them: recolour the same layout by the communities detected in the link graph itself. That number is 35.0% across 11 communities (chance ≈ 9%), and the bands are visible in the picture.

So the concept links do encode real grouping — it is simply not the topic grouping. The two views were derived from different evidence, text versus extracted concepts, and they disagree about how the portfolio divides. Both colourings ship, because the disagreement is the finding. It is also the same lesson as Chapter 3, arriving a second time by a different route: the extracted graph describes tooling, and tooling is not subject.

Decisions I would defend, and one I would revisit

  • Splitting "what is it about" from "what does it use". The whole project turns on this. Text clustering answers the first; the extracted graph answers the second. Forcing either to answer both produces confident nonsense.
  • Selection rules chosen before seeing results. "First Louvain resolution landing in 8–16 communities", "smallest cutoff under the node budget", "k=14 judged by interpretable terms" — picked in advance so the output is not tuned to flatter.
  • Keeping the failed clustering script on disk, labelled. It documents a failure mode that would otherwise be rediscovered.
  • Shipping the disagreement rather than the prettier view. Both colourings, both numbers, in the page and in this document.
  • Verification by observed effect, never by clean exit. Screenshots for rendered pages, measured node positions for physics, printed counts for every build.
  • Would revisit: the 3.4M-token extraction. It bought genuine hub/bridge/orphan structure and a second opinion that turned out to be informative — but for the question that was actually asked, a local pass on the same corpus would have answered it in seconds for nothing. Budget first, extract second.

Things worth knowing before touching any of it

  1. Generated pages are never edited directly. Both HTML deliverables are built by injecting data into a template. Edits go to the template or the build script, then rebuild; direct edits are overwritten.
  2. Every page embeds a snapshot. Regenerate the corpus or the merged data and both pages are stale until rebuilt.
  3. The projection rule is duplicated across the clustering script and the graph build script. Change one, change both, or the picture and the clusters stop describing the same graph.
  4. Both graph colourings reuse one palette function. Cluster 3 and community 3 are the same hue and mean different things; the legend always describes subject clusters.
  5. Embedded JSON and the inlined library both escape </. Without it a repository name containing a closing script tag would truncate the page — the classic single-file HTML foot-gun.
  6. The graph tab burns CPU while open (hover highlighting requires continuous redraw) and re-runs the layout on every load — positions from dragging are not saved.
  7. Search sees only visible nodes. Cluster filters and the orphan toggle change what is findable.
  8. "Derivative" is a name-and-description heuristic, not a provenance check.
  9. There is no git history. The files on disk and the handoff note are the entire record — which is why both are written as if for a stranger.
